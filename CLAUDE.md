# WarpDiff

A/B comparison tool for images, video, and audio. Hosted on GitHub Pages.

- **Repo**: https://github.com/jayriddle/warpdiff
- **Architecture**: `index.html` holds all the HTML/CSS and the bulk of the JS (one `<style>` block top, one `<script>` block bottom), with cohesive subsystems progressively extracted into classic `<script>` files in `js/` (see below). The extracted files are **not ES modules** — they share one global scope with the inline script (top-level `let`/`const`/`function` are visible across all classic scripts in the realm), so an extracted function can read/write inline globals and vice versa, resolved at call time. This is the only viable split given the no-build-step constraint.
- **PWA**: `manifest.json`, `sw.js`, `icon-192.png`, `icon-512.png` — installable, offline-capable.
- **No build step**: vanilla HTML/CSS/JS only, served as static files. **One deliberate exception**: `version.json` carries Jekyll front matter so GitHub Pages substitutes `{{ site.github.build_revision }}` (the deployed commit SHA) at deploy time — the only way to identify the served build, since a commit can't contain its own hash. The app fetches it and appends the short hash to the version display (`v3.11.6 · a2e5aa7`); local dev / offline-miss get the raw file (JSON.parse throws on the front matter) and show the bare version. **Never add a `.nojekyll` file** — it would silently kill the substitution (harness-guarded). `_config.yml` excludes all `.md` docs (and tests/tooling) from the Pages build: themed `.md` pages invoke `{% seo %}` → jekyll-github-metadata → a **GitHub API call at build time**, which failed whole deploys during API incidents (2026-07-16). Keep the exclude list (harness-guarded); the docs are read on github.com, not the live site.

### Files

- `index.html` — the app. One `<style>` block at the top, one `<script>` block at the bottom.
- `js/audio-viz.js` — waveform/spectrogram FFT, K-weighting biquads, EBU R128 LUFS/LRA/True-Peak computation, palette tables. Exports functions consumed by the script in `index.html`.
- `js/scopes.js` — video scope rendering (waveform monitor, histogram, vectorscope). Uses `Uint16Array` hit-count buffers + `putImageData`; buffers cached across frames, reallocated on resize.
- `js/hotkeys.js` — registry-based hotkey table + key→action lookup, with localStorage override for custom bindings.
- `js/mp4-demux.js` — pure MP4/WebM audio demuxers (`_demuxMP4Audio` / `_demuxWebMAudio`) plus the video sample-table demuxer for scrubbing (`_demuxMP4Video`: stsd/stss/stsz/stsc/stco/stts/ctts/elst → decode-order samples with elst-shifted pts, avcC/hvcC config, RFC 6381 codec strings). No app-state deps.
- `js/scrub-video.js` — WebCodecs scrub decoder sessions (`_createScrubVideoSession`): per-slot VideoDecoder, GOP-run feeding with reorder margin, rAF-coalesced painting, decoded-frame ImageBitmap cache (distance-gated: frames the eviction policy would immediately discard are never cloned/bitmapped — reverse scrubs re-decode whole GOPs and would otherwise churn dozens of `createImageBitmap`s per step). **The cache budget is sized to the file's longest GOP** (96 MB floor → 192 MB ceiling, ~27→54 frames at 1280×720), because a decoder only runs forward: any backward target the in-flight run has already passed costs `reset()` + a re-decode from the keyframe, so backward travel is free only while that run's frames are still cached. A flat 96 MB held 27 frames against a 48-frame GOP, so a backward drag fell off the window every ~27 frames — measured (real Chrome, two 10 s 1080p clips, median of 3 drags of 61 requests): **15 resets / 500 `decode()` / 32 visible stalls → 8 / 285 / 18** once the cache spanned the GOP. Forward drags are identical either way (5 resets) since they extend the run instead of restarting it — that asymmetry is the whole bug. **Request coalescing was tried and is a REGRESSION** (rAF-batching drag requests added a frame of latency to every scrub, p50 0.2 → 8.3 ms, and left reset counts unchanged — the reset count is driven by how far each target jumps, not how many requests arrive); don't reintroduce it. **Predictive backward prefetch** (v3.12.7) closes the follow-on gap: sizing the cache to a GOP made backward travel free *within* a GOP, but every GOP boundary crossed backward still cost a full re-decode (~100 ms at 2560×1440 — 7–9 of 61 drag requests painted nothing at all). So when `scrubDir < 0` and a request is served **from cache** (decoder idle, user coasting), `maybePrefetchBackward` speculatively decodes the *previous* GOP via `startPrefetch`; `runIsPrefetch` makes those frames cache-only, never painted (they're the past relative to the viewport). Any real target clears the flag and reclaims the run. **`PREFETCH_LEAD` must scale with the GOP** (`maxGop * 0.6`): a flat 12 frames (~45 ms of lead) fired on schedule but the ~100 ms decode landed late, so the user stalled on the prefetch run instead of a fresh one and stalls barely moved (21 → 19). Measured at 2K, median of 3 runs × 2 backward drags: **stalls >33 ms 17.5 → 10.5, freezes 6 → 4.5**; 1080p 6–7 → 3–5 with 98–100% cache hits. Also tried and **reverted**: caching only the *tail* of the speculative GOP (to stop it evicting the GOP still in use) — it cost the long-drag win (freezes 0 → 2, hits 100% → 92%) without fixing the short-drag case. **Separately, 4K scrubbing is decode-throughput-bound in BOTH directions** and the cache budget is not the lever: measured on two 3840×2160 clips, 21–35 of 61 drag requests stall >33 ms and 10–24 paint nothing at all, roughly the same at a 96 MB or a 190 MB budget (the per-frame bitmap is capped at 1280×720 either way, so the cache doesn't grow with source resolution — what grows is decode + `createImageBitmap` resize cost). Fixing that needs a different approach (decode a reduced-resolution preview, or skip frames under load), not a bigger cache. Sessions **suspend** on playback start (`suspend()` closes only the VideoDecoder — the hardware pipeline that starves playing `<video>`s — keeping file bytes, demux, and frame cache; `request()` lazily resumes in ~ms) and fully `close()` only on media clear. Consumed by the overlay controller in `index.html` (`_suspendScrubSessions` from `playAllMedia` vs `_releaseScrubSessions` from `clearAllMedia`). No app-state deps (canvas injected via `attach`).
- `js/timecode.js` — pure timecode formatters (`_formatTcForCopy`, `_formatTcForMarker`); only app dep is the `_prefs.load` default-format lookup. State-coupled builders stay inline.
- `js/opus-sync.js` — the Chrome Opus A/V sync engine (`_opusSync*` state, `_startOpusSyncAudio`/`_stopOpusSyncAudio`/`_syncOpusAudioToVideo`/`_updateOpusSyncRate`/`_updateOpusSyncGains`, `_OPUS_FADE`). **Stateful** (shares globals). Owns the deferred-start-window invariant (see below).
- `js/audio-decode.js` — the three-tier audio decode pipeline: `decodeAndComputeAudioViz`, `decodeAndComputeAudioSlotViz`, `_decodeAudioWebCodecs`, `_decodeWithAudioDecoder`, `_finalizeAudioViz`, `_onAllDecodeFailed`. **Stateful** — reads/writes inline globals (`mediaData`, `_opusSync*`, `waveformData`, the two decode-generation counters) via shared global scope.
- `js/transport.js` — playback/transport: `playAllMedia`/`pauseAllMedia`/`restartAllVideos`, `stepFrame`, `syncVideos`/`syncMedia`, frame-accurate loop enforcement (`_startLoopRvfc` + `_loopWrapTimer`), the multi-video sync-lock cluster (`_getLoopBounds`/`_applyNativeLoopPolicy`/`_driftLockTick`), and video/audio handler binding (`setupVideoHandlers`/`setupAudioHandlers`/`_setupFpsDetection`). **Stateful** (shares globals). Holds the single-owner targets for the ownership guards.
- `js/starfield.js` — landing-page background animation.
- `ffmpeg/` — ffmpeg.wasm bundle (`ffmpeg-core.{js,wasm,worker.js}` + `ffmpeg.min.js`, ~24 MB). Loaded lazily, single-threaded (no `crossOriginIsolated` / `SharedArrayBuffer`).
- `tests/` — `warpdiff.spec.ts` (Playwright) + `ownership.test.mjs` (dependency-free Node harness; see Testing) + a set of hand-run investigation harnesses (not CI — they need headed browsers and realistic media). Real Chrome: `investigate-pause-hop.mjs` (play/pause drift + convergence), `investigate-step-sync.mjs` (frame stepping and long-run drift across a 24/25/29.97/30 fps matrix), and `investigate-transport-sync.mjs` (playback rate 0.25×–2×, scrubbing forward/backward, mid-playback asset switching, zoomed switching — run it at 1080p and 4K), and `investigate-scrub-reverse.mjs` (forward-vs-backward scrub cadence). Real **Safari** via `safaridriver` W3C HTTP (Playwright cannot drive shipping Safari): `investigate-safari.mjs` (geometry / RVFC deltas / cadence / hitch attribution), `-successive.mjs` (per-cycle drift+bad-steps, `MODE=` policy arms), `-startup.mjs` (offset formation), `-switch.mjs` (Stack A/B switch arms), `-loop.mjs` and `-baseline.mjs` (no-WarpDiff controls), plus `safari-loop-check.html` — a standalone page the user opens directly, which removes the automation and HTTP-Range confounds that made three earlier cross-context conclusions wrong. The investigation harnesses are run by hand, not by CI — they need headed Chrome and realistic media (see `docs/pause-hop-investigation-2026-07.md`; the repo fixtures are far too small to reproduce decode-timing bugs). `tests/global-setup.ts` auto-generates the gitignored MP4/WebM/WAV/MP3 fixtures via `tests/fixtures/generate.sh` on first run (requires `ffmpeg` on PATH). The H.264 MP4 fixtures need a proprietary-codec Chrome; the VP9+Vorbis WebM fixtures exist so the 2026-07 regression suites (scrub-drag recovery, pause snap, switch repaint, **loop in/out, multi-video sync-lock, spectrogram render**) also run on open-codec Chromium builds — Vorbis deliberately, since Opus slots take the Web Audio path where `.muted` is always true and the muted-flag tests would be vacuous. Three WebM clips: `vorbis_a`/`vorbis_b` are 3 s (equal length) and `vorbis_long` is 4 s — the sync-lock tests that assert `[0, shortest]` bounds and shortest-clip wrap need an unequal pair, so they load `vorbis_a` + `vorbis_long` (the open-codec analogue of the `landscape_a` 3 s / `landscape_b` 4 s pair).

**When extracting more code into `js/`** (candidates: layout-geometry pure math, waveform/spectrogram panel drawing → `js/audio-viz.js`, ffmpeg transcode orchestration): keep the function definitions in the module, leave the call sites + a `// name → js/file.js` pointer comment in `index.html`, add a `<script src>` tag *before* the inline script, **and add the file to `sw.js` ASSETS** (guarded by the ownership harness). The harness reads concatenated sources, so its guards keep resolving moved functions without edits.

## Key Technical Patterns

### Frame & timecode
- Frame stepping uses midpoint seeking `(frame+0.5)/fps` to avoid IEEE 754 boundary issues.
- **`stepFrame` is reference-driven** (v3.12.5): it advances the reference clip (`_syncReferenceVideo` — the same selected-clip owner `_snapAllVideosToFrame` uses) by one of *its* frames, then quantizes every clip onto its **own** grid at that shared time. It previously stepped each video from its own clock by its own `fps`, so a mixed-fps pair diverged by the frame-duration difference on **every step** (24 vs 30 fps = 8.3 ms/step → ~5 frames adrift after 24 taps; measured 204 ms), and nothing corrected it — the drift lock only runs while playing and the pause snap only runs from `pauseAllMedia`. Its per-clip `% totalFrames` wrap was the same bug at the loop point: clips of different lengths wrapped at their own ends onto unrelated content (measured 2.9 s apart). A follower shorter than the reference now clamps to its last frame instead of wrapping. Guarded by the ownership harness (`one-owner[sync-ref]`, `step-sync`) and a mixed-fps Playwright regression test (`vorbis_a` 24 fps + `vorbis_30` 30 fps).
- **Repeated `,` / `.` presses use a burst-local logical frame cursor** (v3.12.16). During a precise seek, Safari/WebKit can keep reporting the previous settled `currentTime`; calculating the next press from that stale value requests the same frame again. `_frameStepCursor` advances from the last requested reference frame while its seek is unresolved (or has just landed), expires after 750 ms, and resets on playback, pause, restart, and both scrub entry points. Ordinary settled seeks therefore remain authoritative. Guarded by `one-owner[frame-step-cursor]` plus rapid-step Playwright coverage.
- Timecode display uses `Math.floor(time * fps + 0.01)` epsilon to match frame numbers.
- `_frameStepping` flag pattern suppresses play/pause sync handlers during programmatic seeks.
- Passive fps detection (`_setupFpsDetection`) records frame intervals via `requestVideoFrameCallback` during normal playback, snaps to standard rates (23.976 / 24 / 25 / 29.97 / 30 / 48 / 59.94 / 60). No active probing at load time. **The frame duration is the MEDIAN interval, never the minimum** (v3.12.8): the minimum is the least robust statistic available, and one spuriously small delta sets the dropped-frame threshold for every other sample, so all the real intervals get discarded as "drops" and the estimate collapses onto the junk. Safari emits exactly that during ordinary playback — measured in real Safari on a 24 fps clip, a clean run of 41.67 ms deltas polluted by 2.17 / 4.65 / 0 / −666 / 743 ms values; `min` → 2.17 ms → threshold 3.26 ms → **zero** real intervals survived → ~460 fps, snapped to **60** (Chrome read the same file as 24), which then fed the wrong grid to `_snapAllVideosToFrame` and `stepFrame`. Kept intervals are within ±25% of the median (a real dropped frame lands at ~2×). Guarded by pure-function tests in the ownership harness that replay Safari's actual deltas. Intervals **accumulate across play sessions** (`lastTs` anchors the current run; `'play'` and `'seeking'` only drop the anchor, never the samples): detection needs `_FPS_SAMPLE_COUNT` frames (~1.3 s at 24 fps) and the old per-`play` reset meant a user reviewing in short taps (~0.7 s) never completed a pass, leaving the clip pinned to the 30 fps default — which then fed the wrong grid to `_snapAllVideosToFrame`'s `(frame + 0.5) / fps` quantization and the wrong half-frame band to the drift lock (v3.12.5).

### Layout
- Stack mode `applyZoom()` supports two zoom reference modes toggled by `\` (`_stackZoomMode`):
  - **Fit** (default) — `_perAssetFits[slot] = min(viewW/nw, viewH/nh)`; `fitZoom` = smallest per-asset fit; each asset fills the viewport independently.
  - **Match** — `fitZoom = _perAssetFits['original']`; all assets rendered at the GT slot's fit scale so spatial scale is consistent across assets. Only available when the GT slot is loaded; `_toggleStackZoomMode()` no-ops with a toast otherwise. Pill indicator in header shows `Fit` (gray) or `Match · GT` (orange).
- Equal-area layout for mixed orientations (Grid inline mode): `A = min((availW/Σ√ri)², availH²·min(ri))`.
- Grid layout auto-picks horizontal vs vertical via `pickBestGridLayout(n)` — computes rendered area for each option given viewport dimensions and asset aspect ratios; re-evaluated on resize.
- **Group centring in the equal-area path centres the grid TRACKS (`justifyContent`), never the pictures inside their cells** (v3.12.8). Each `.asset-layer` is sized to exactly its rendered picture, so the picture sits at its layer's origin (`tx = (cw − rw)/2`, normally 0). The old code centred the group by offsetting each picture *within* its cell (`tx = viewport-centred group start − running cell left`) — which moves the `<video>` but **not** the `.asset-layer` that carries the click-to-select listener, so the picture overhung into the neighbouring layer and clicking a video selected the WRONG slot (clicking the empty strip beside it still worked). Chromium masked it: there the cells nearly fill the viewport so the offset was ~8 px. A portrait + landscape pair in Safari left 624 px of slack → a 312 px shift, the reported bug. The old walk was also inconsistent about the gap (`cumImgLeft` added it, `cumCellLeft` didn't), so the error grew by one gap per slot. Guarded by a mixed-orientation Playwright test asserting each video's rect stays inside its layer's and that the picture's centre hit-tests to its own layer.
- Three-phase layout: measure → compute geometry → DOM write. Debounced functions use the pattern `functionNameDebounced` wrapping `functionName`.

### Loop region & multi-video sync-lock
- **`_getLoopBounds()`** (`js/transport.js`) is the single source of truth for "where does playback wrap": custom in/out points win; otherwise, with 2+ videos loaded, all videos loop **together** over `[0, effective duration]` where the duration is the **shortest** clip in `_loopRangeMode === 'sync'` (default — frame-locked A/B) or the **longest** clip in `'full'`; single video / audio mode / metadata-not-ready → `null` (plain native looping). Native per-element loop with 2+ videos is the biggest desync source — each element wraps at its own duration on its own clock and the offset compounds every pass.
- **Loop range mode** (`_loopRangeMode`, toggled by `_toggleLoopRangeMode` / Shift+L / the `#loopRangeBtn` transport pill; resets to `'sync'` in `clearAllMedia`): **Full** mode reviews clips of different lengths in full — a clip that reaches its own end **holds on its last frame** and the group wraps only once **every** clip has ended (the longest finishing is the trigger). This wrap is deliberately **event-driven** (the `'ended'` all-ended gate in `setupVideoHandlers`), *not* a per-frame `currentTime` comparison — an earlier `allStopped`-in-rAF design raced the drift lock and wrapped early. `_loopWrapToInPoint` seeks **and** plays every element so the frozen (ended) clips resume on wrap. `updateLoop` substitutes a still-playing clip as the progress driver during the tail (`_loopTail`) so the bar/loop stay alive while the active clip is frozen — progress keep-alive only; it does not drive the wrap. **Default policy**: clips that **differ in length default to Full** (set once at load by `_notifyDurationMismatch`, which also pulses the pill via the `.attention` class and toasts the control); equal-length clips stay `'sync'`. `Shift+L` opts into Sync for a tight frame-locked comparison loop.
- **Shared loop points**: `_loopInPoint`/`_loopOutPoint` are **global**, applied to every clip and kept across asset switches (there is no per-slot loop store — the old `_loopPointsPerSlot` swap in `switchToAsset` was removed; setting one region for all clips is the typical A/B need). `_notifyDurationMismatch` (from `startFadeIn`) shows a one-time toast when loaded clips differ in length. **Excluded-tail cue**: `updateLoopMarkerUI` hatches a `#loopTailBand` over the part of the *active* clip that runs past the loop's out-point — i.e. Sync mode with a clip longer than the shortest, where content past the band isn't looped (Full mode wraps at the longest, so the active clip never exceeds the loop → no band).
- **`_applyNativeLoopPolicy()`** is the sole writer of the managed `.loop` flag (`native = bounds === null`); every path (marker set/clear/drag, shift+drag region select, asset switch, `loadedmetadata` via `setupVideoHandlers`, `playAllMedia`) routes through it. (The scrub handlers' temporary `v.loop = false` during a drag is a scoped override, restored via the policy on resume.) Guarded by the ownership harness (finding H).
- **`_driftLockTick(primary)`** (called every rAF from `startProgressUpdateLoop`) holds followers on the primary's clock via `playbackRate` trims in **both** modes, hard-seeking only past `_DRIFT_HARD_SEEK` (150 ms — missed wrap / stall): Grid followers are visible, so they get a **proportional** trim — `mag / _DRIFT_CONVERGE_TAU` (0.4 s), floored at `_DRIFT_NUDGE` (±2%) and capped at `_DRIFT_NUDGE_MAX` (±12%) — while Stack's follower is `display:none` **and** muted, so it gets a flat strong ±10% (`_DRIFT_NUDGE_HIDDEN`) with zero perceptible cost. Grid's trim was a flat ±2% until v3.12.5, which was right for steady-state drift but **5× too weak for the real problem**: two `<video>`s told to play together come up **1–2 frames apart** on real hardware (a decode-start race, not drift — measured in real Chrome on 1080p high-bitrate H.264, the offset builds to 35–50 ms within the first ~200 ms and then just sits there). Flat ±2% needed ~1.5 s to walk 45 ms out (measured: converged at 1494 / 1643 ms), but a review pause typically lands ~0.7 s in — while the pair is still >½ frame apart, so `_snapAllVideosToFrame` correctly seeks the follower and **that seek** is the visible "B stutters a frame or two to catch up on almost every pause" hop (the reference is never seeked, hence the asymmetry and why it tracks the selection). Proportional trim closes the same 45 ms in ~0.3 s (measured: 0/10 pauses seek, vs 6/10 before) and still nudges small errors at the old gentle ±2%, so the visible follower only ever gets a strong trim when it is already a frame out — exactly when the alternative is a worse-looking seek. Verified not to cost frame-pacing: at a 12% trim the follower's presented-frame cadence is indistinguishable from the untouched primary's (clean run: both a flat 41.67 ms at 24 fps). **These are per-play-session offsets — don't "fix" this by tightening the pause snap; that's the symptom, not the cause** (v3.12.3 and v3.12.4 both tried and neither changed what the user saw). **WebKit: trims on a VISIBLE follower are an UNSTABLE control loop — suppressed there (v3.12.11, `_RATE_TRIM_IS_SMOOTH`, capability-detected via `fastSeek`).** Safari presents a rate-trimmed visible follower unevenly at ANY magnitude (2/5/12% equally bad — measured v3.12.9: 12/102 bad frame-steps vs the untrimmed primary's 0), each stutter loses real time, and the loss keeps the trim engaged: **the trim feeds the drift it corrects.** Measured via `tests/investigate-safari-successive.mjs` (6 play/pause cycles per arm, real Safari, 2K): shipping trims → peak drift 122–142 ms and 10–15 bad frame-steps per ~90 whenever the lock engaged (cycles that started inside the engage band stayed clean at 20–30 ms — the "first play smooth, later plays stutter" report); **no correction → drift settles at ~50 ms (≈1 frame) and HOLDS, 1/83 bad steps every cycle.** Doing nothing beats trimming on both axes. A contaminated arm double-confirmed the mechanism: a follower stuck at a constant 12% skew (drift growing 133 ms/s) still presented smoothly — rate *churn* stutters, wrong rate doesn't. So WebKit visible followers get no trims, plus a **stability-gated hard-seek** (`_WK_SEEK_STABLE_TICKS` consecutive ticks past `_DRIFT_HARD_SEEK` + `_WK_SEEK_COOLDOWN_MS` cooldown, with the `_seekLead`) so a start-up stall that pushes drift past 150 ms is corrected once, never a storm — the un-gated seek was the missing piece when v3.12.9 shipped the trim gate alone and failed on real footage. At pause the clocks settle and the pair typically reads <10 ms apart → same frame, snap skips, no hop. **WebKit trims nothing at all as of v3.12.12** — Stack's follower included: on WebKit inactive Stack wrappers stay COMPOSITED (see the Stack-switch bullet), so the "hidden" follower is presenting, and even fully invisible the trims churned it (`tests/investigate-safari-switch.mjs`: composited+trims still hesitated ~100 ms at an A/B switch with a trim active on 7/8 switches; composited+untrimmed presented the first new frame in ≤40 ms with 0 bad steps). Chrome (`_RATE_TRIM_IS_SMOOTH` true) is unchanged everywhere. **What remains on Safari and is the ENGINE's, not fixable by sync policy:** 2–3 decode-warm-up hitches at play start (present in every measured arm), and the unmuted loop-restart stall (~117–133 ms on 5/5 wraps on a bare page with zero app code — user-verified via `tests/safari-loop-check.html`; muted loops are clean). Guarded by four `drift-lock[webkit]` ownership cases. Harnesses: `tests/investigate-safari.mjs`, `tests/investigate-safari-successive.mjs` (per-cycle drift/trims/bad-steps, `MODE=baseline|noTrim|oneShot` in-page policy patches — **reset follower `playbackRate` when patching**, a stub that never writes rates freezes in whatever nudge the warm-up left), `tests/investigate-safari-startup.mjs` (offset formation; also disproved a start race — readyState 4/4, `play()`/`playing` within 1 ms, clocks moving within 6–17 ms; the offset forms ~200–300 ms in when the follower briefly stalls). **Measurement lesson (cost three wrong conclusions): use presented-content metrics** — RVFC `mediaTime` steps ("bad frame-steps": the picture repeating/skipping) track what the user sees; wall-clock RVFC gaps and cross-context bare-page comparisons repeatedly did not (a "617 ms bare-page stall" was the harness serving media without HTTP Range support; a muted-vs-unmuted mix-up produced "it's WarpDiff, not Safari"). **Rate interaction — verified, don't "fix" in isolation:** the trim is a *fraction* of the base rate, so convergence time is `TAU/base` — 1.6 s at 0.25×, 0.2 s at 2×. That's fine, because the startup offset scales with rate too (measured peak drift 2.5 ms at 0.25× → 23 ms at 2×): the two cancel, and every rate 0.25×–2× pauses within half a frame at 1080p and 4K. A rate-independent trim would make the fast rates overshoot. **Never hard-seek a playing follower for sub-threshold drift**: a seek stalls the element for its seek latency, landing it *behind* by more than the engage threshold again — a perpetual seek loop (~26 seeks/s measured) that pinned Stack's hidden follower 1–2 frames behind, so every mid-playback asset switch promoted the laggard to clock master and dragged the whole cluster backward (the 2026-07 "switching jumps back a frame and stalls" bug). The rare legitimate hard-seeks compensate the same physics by **leading** the target with the adaptively-measured landing error (`v._seekLead`, folded at 0.8 gain, capped 250 ms). The engage threshold is computed **per follower** at `min(primary fps, follower fps)` so a low-fps follower under a high-fps primary isn't re-engaged every tick (thrash) — except Stack tightens it to **8 ms** (nudges are free on a hidden+muted element, and the follower is what a switch reveals, so tolerated drift becomes a visible content offset on near-identical clips). A lower hidden-seek tier (~40 ms) was tried and **measured worse** (seek-latency jitter re-triggers around a low bar — see the `_DRIFT_HARD_SEEK` comment); don't reintroduce it. The nudged rate is re-asserted each tick so a J/K rate write mid-episode can't strand a follower at the base rate; it stands down during `isDragging` / `_bulkSyncActive`. The clock-master base is read from the user-selected rate (`PLAYBACK_RATES[playbackRateIndex]`), not `primary.playbackRate`, and the primary is forced onto it (nudge cleared) each tick — otherwise an asset switch that promotes a mid-nudge follower to primary would strand the whole cluster at ±2% (a global tempo skew, audit finding C1).
- **Matched-pair diff gate**: `drawDiffComposite` returns early (holding the last composite) when the two videos' clocks are ≥ half a frame apart (`_diffFramesMismatched`) — a mismatched pair renders as motion ghosting that reads like codec error. Clock-based deliberately: `drawImage` samples the element's current decoded frame (which tracks `currentTime`, not the compositor), and RVFC never fires for Stack mode's `display:none` follower. Always draws when both videos are paused (frame stepping must refresh the diff).
- **Seamless mid-playback Stack switch**: `_beginSeamlessSwitch()` (`index.html`, sole caller `switchToAsset`, Stack + playing only). **Chrome-only as of v3.12.12** — on WebKit it early-returns, because the problem it papers over doesn't exist there anymore: WebKit takes **100–500 ms to resume presenting a `display:none`'d `<video>`** (measured first-new-frame after a Stack A/B switch: p50 138–298 ms, worst 479–761 ms — the reported Safari "hesitation when switching A↔B", present in a `muted` arm too, so NOT the audio pipeline), so `body.webkit-video` (set at boot from the same `fastSeek` capability as `_RATE_TRIM_IS_SMOOTH`) overrides the wrapper `display:none` to `display:block` and lets the parent `.asset-layer`'s existing `opacity:0` + `pointer-events:none` do the hiding — the element stays composited and never stops presenting, so a switch reveals a live surface (measured shipped: p50 **12 ms**, 7/8 switches ≤27 ms, 0 trims, full-rate presentation; needs the WebKit no-trim policy too — composited-but-trimmed still hesitated ~100 ms). The black-A-slot compositor hazard that forced `display:none` is Chrome-on-macOS-specific, so Chrome keeps `display:none` + the double-buffer (re-verified: 0.01–3.2 ms switch drift, clean at 3.75× zoom). Guarded by three `webkit-switch` ownership checks (CSS override / boot class / bypass all key on the same capability). A `display:none` `<video>` keeps its clock but stops being **presented** — unhiding it flashes the stale frame from when it was last visible (a backward jump on near-identical clips) and stalls while decode catches up. So the **outgoing** layer keeps `.switch-out` (visible, wrapper `z-index` above the incoming, still playing) until the incoming video's RVFC presents a frame whose `mediaTime` matches its `currentTime` (the stale frame Chrome presents on unhide is filtered out and re-armed past). A **300 ms hard fallback** bounds the transient two-video compositor overlap (the macOS black-A-slot hazard — see the CSS note); rapid switches invalidate prior swaps by token. Guarded by ownership harness (M).
- **Pause-time frame snap**: `_snapAllVideosToFrame()` (`js/transport.js`, sole caller `pauseAllMedia`) quantizes every video to its **own** frame grid at the reference clip's paused `currentTime`, immediately after all videos are paused. The drift lock only holds followers within tolerance (half a frame Stack / ~5 ms converged Grid) *during* playback — tight enough to look synced, but a clip a few ms off can straddle a frame boundary and round to frame N vs N+1 at the exact instant `pause()` lands. Uses the reference's **time**, not its frame *number* — clips can differ in fps, so each follower is independently quantized (mirrors `stepFrame`'s midpoint-seek math, `(frame + 0.5) / fps`). **Only seeks a follower that is MORE than half a frame off the reference** (`Math.abs(v.currentTime − refTime) <= 0.5 / fps` → skip). Two rounds of narrowing got here: `currentTime` is virtually never exactly at a frame midpoint, so the original `|currentTime − midpoint| > 1e-4` guard re-seeked *every* clip on *every* pause (the reference included) — a seek on a just-paused clip forces a re-present that visibly jumps the picture ±1 frame as the decoder catches up. v3.12.3 switched to a frame-*number* compare, which stopped seeking the reference (it's always on its own frame) but still seeked a **follower** that straddled a boundary — and since the reference stays solid while the follower hops to catch up, that read as an asymmetric "the non-selected clip stutters on almost every Grid pause" bug (v3.12.4). The drift lock never holds followers tighter than half a frame *during* playback anyway, so a within-tolerance follower is left exactly where it froze (at most one frame off, but motionless); only a genuinely unconverged follower (>½ frame, e.g. paused right after play/seek/loop-wrap) is snapped onto the reference frame. No-op for audio mode, fewer than 2 videos, or during a drag (the scrub-start pause routes through `pauseAllMedia` and the snap's seeks would race the drag's first seek).

### Loop enforcement (RVFC chain)
Loop-region wrapping (custom in/out points *and* the multi-video sync loop) is enforced *frame-accurately* via `requestVideoFrameCallback`, not rAF — in **both** view modes (the chain lives on the primary video; the wrap seeks every video, which is mode-independent). `startProgressUpdateLoop` re-arms `_startLoopRvfc(primary)` every tick (idempotent via the per-video ownership flag) so the chain stays attached across asset switches and mode changes, which don't re-fire `'play'`; the rAF check in `updateLoop` remains as the fallback for browsers without RVFC.

- `_startLoopRvfc(video)` registers an `onFrame` callback that checks `metadata.mediaTime` against `_getLoopBounds()` and seeks back when out of range. The callback always re-registers itself at the end (single chain, no duplicate callbacks).
- **Scheduled exact-time wrap**: `mediaTime` is quantized to the frame grid, so waiting for a frame *past* the out-point lets up to a full frame of audio (~42 ms at 24 fps, plus seek latency) play beyond the boundary — audibly. When the **last in-region frame** presents (`t >= out − frameDur·1.25`, `frameDur` from `videoFrameRates`), `onFrame` schedules `_loopWrapToInPoint()` via `setTimeout` for the exact out-point time (playback-rate aware). The timer re-validates before firing (loop cleared / paused / user seeked back) and is cancelled by `clearLoopMarkers`; the immediate `t >= out` check remains as the safety net.
- **Critical**: never register both `requestVideoFrameCallback` *and* an `'ended'`/`'playing'` event listener as fallbacks at the same site — they create parallel chains on stall and dead chains on non-stall. RVFC's contract is "fire when next frame is presented," which covers both the post-seek and post-stall cases on its own.
- The `'play'` event handler in `setupVideoHandlers` must start the RVFC chain **before** the `_bulkSyncActive` early-return; `playAllMedia` flips that flag for 50 ms and the chain would otherwise never start.
- `playAllMedia` calls `_applyNativeLoopPolicy()` (never writes `.loop` itself) — native loop with a managed region active fights the synchronized seek-back.
- `setLoopPoint` clamps `media.currentTime` to `_getEffectiveDuration(media)` before storing, so loop markers don't overflow the timeline for files where `video.duration` is inflated past actual content (e.g. Opus / DTS with audio-extension metadata).
- A `'ended'` handler wraps to in-point when a managed loop region is active — the RVFC out-point check fires on `mediaTime >= outP`, but the last frame's `mediaTime` is typically one frame *short* of duration, so an out-point at a video's effective end never trips the check and that video ends instead. The handler restarts everyone at in-point; with unequal durations the shortest video's `ended` drags the rest back (sync loop).

### Audio decode pipeline (three-tier)
1. **`decodeAudioData()`** — native browser decode. Race against a timeout: 1 s if WebCodecs is available (fast fallback), 30 s otherwise.
2. **WebCodecs `AudioDecoder`** — for codecs `decodeAudioData` doesn't handle (notably Opus in Safari, and Opus in Chrome where decode is "successful" but timing is wrong). Demuxer (`_demuxMP4Audio` / `_demuxWebMAudio`) extracts packets manually.
3. **ffmpeg.wasm transcode** — last resort for unsupported codecs (AC-3 / EAC-3 / DTS family / TrueHD).

The fallback routing is **`_onAllDecodeFailed(slot, audioConfirmed)`**:
- If `audioConfirmed=true` (WebCodecs already extracted packets but couldn't decode them — e.g. DTS-HD MA muxed with `mp4a` fourcc, malformed AAC, HE-AAC marked as LC), always attempt transcode.
- If `audioConfirmed=false` and the byte scanner didn't find a known unsupported-codec signature (`ac-3` / `ec-3` / `dtsc` / `dtse` / `dtsh` / `dtsl` / `mlpa`) inside MP4 box atoms, *and* the file is a video, treat as "no audio track" and skip transcode. (Without this distinction, files with confirmed-but-undecodable audio get silently dropped.)
- Otherwise call `_registerFfmpegCommand` which queues the slot for transcode and pops the ffmpeg panel.

### MP4 audio demuxer (`_demuxMP4Audio`)
- Walks `moov → trak → mdia → mdhd / hdlr / minf / stbl → stsd / stsz / stco / co64 / stsc / stts` and `trak → edts → elst`.
- **Per-track scoping is mandatory** for `mdhd.timescale`. Store in `_lastMdhdTimescale` during `parseMdhd` and only promote to the demuxer-wide `timescale` inside `parseHdlr` when `handler_type === 'soun'`. A previous version used a single global `timescale` that got overwritten by every track visited — so a data/subtitle track at timescale=1000 silently clobbered the audio track's 48000, making elst priming offsets (16512 / 48000 = 344 ms) look like 16.5-second skips. Same scoping for `_lastElstMediaTime` and `_lastElstSegDuration` (these reset at each `parseTkhd`).
- Returned `extracted` shape: `{ chunks: [{timestamp, data}], sampleRate, channels, codec, description, preSkip, maxSamples, timelineStart }`. `preSkip` and `maxSamples` are applied post-decode to trim encoder priming and edit-list-truncated tails. `timelineStart` is the sum of leading empty edit-list entries (`media_time === -1`) in movie timescale units; decoded scrub audio and Chromium's Opus replacement subtract it when mapping video time to buffer time. `_demuxMP4Audio(data, true)` is the metadata-only path used before `decodeAudioData`: it walks only track timing boxes and does not build/copy audio packets.

### ffmpeg.wasm transcode
- Loaded once (~24 MB), single-threaded (the bundled build is built with `--disable-pthreads`). Each `ff.run()` invocation exits the wasm instance, so `_ffmpegLoaded` and `_ffmpegInstance` are reset after every run and the next slot in `_ffmpegQueue` triggers a fresh load.
- `_ffmpegQueue` is sorted by `assetOrder` on each push so Ref → A → B order is preserved regardless of which decode fails first.
- Standard transcode command (use as a template for unsupported-codec → AAC):
  ```
  ffmpeg -ignore_editlist 0 -fflags +bitexact -i input.mp4 \
         -map 0:v:0 -map 0:a:0 \
         -c:v copy \
         -c:a aac -ac 2 -ar 48000 -b:a 192k \
         -shortest -movflags +faststart \
         output_aac.mp4
  ```
  Critical flags:
  - **`-ignore_editlist 0`** — *apply* the input edit list. DTS-HD MA and similar codecs carry an elst that trims ~344 ms of encoder priming silence; ignoring it (`-ignore_editlist 1`) leaves the priming in the decoded PCM and the output AAC plays late by that amount.
  - **`-ac 2`** — explicit stereo downmix. AAC 5.1 playback in browsers is spotty; stereo is rock-solid.
  - **`-shortest`** — caps output duration to the shortest stream (= video). Otherwise audio overhang produces A/V duration mismatch in the muxed output.
  - **`-movflags +faststart`** — moov atom at the front for streaming.
- `ff.setLogger` captures all output (`fferr`, `ffout`, `info`) regardless of type; on completion the captured stderr is dumped to console as `[ffmpeg] <slot> stderr: …`. Diagnostic surface for transcode-related questions.

### Opus / Chrome Web Audio sync replacement
Chrome's `<video>` element produces incorrect A/V timing for Opus audio tracks. For affected slots we mute `<video>` audio and play the decoded `AudioBuffer` via Web Audio.

- `_opusSyncSlots[slot]` flags the slot as needing Web Audio replacement. `_opusSyncActive` is the global toggle.
- `_opusSyncDuration[slot]` stores the corrected duration from the decoded buffer (raw `video.duration` reflects container metadata that often extends past actual audio end). `_getEffectiveDuration()` returns this for Opus slots, raw `video.duration` otherwise. Used by timeline, loop markers, and info-bar / Stack-strip duration display.
- `_startOpusSyncAudio(slot, fromTime)`: creates an `AudioBufferSourceNode` at the slot's video's `playbackRate`, fades in over `_OPUS_FADE` (15 ms). Starts at `max(now, _opusSyncFadeUntil[slot])` — `_stopOpusSyncAudio` stamps `_opusSyncFadeUntil` whenever it fades an *audible* source, so any stop→start sequence (internal replacement or external pause→play) waits out the fade rather than crossfading uncorrelated audio with it. The buffer offset is advanced by `(startTime − now)·rate` so audio aligns with the still-advancing video at the actual start moment (starting at `fromTime`'s sample would bake a permanent lag into the drift anchors). Records the **scheduled start time** in `_opusSyncStartCtx` (possibly future), start video time, and the rate per slot.
- **Deferred-start window**: for up to `_OPUS_FADE` after replacing an audible source, the new source exists but hasn't started and all its gain automation is in the future (`gain.gain.value` still reads the GainNode default 1.0). Every consumer of the per-slot state must handle `_opusSyncStartCtx[slot] > ctx.currentTime`: `_syncOpusAudioToVideo` skips drift checks (`elapsed < 0`), `_updateOpusSyncRate` skips re-anchoring, `_updateOpusSyncGains` re-schedules the pending fade-in instead of writing `.value`, and `_stopOpusSyncAudio` cancels the scheduled start outright instead of running a value-anchored fade (which would anchor at 1.0 and let the source start un-faded). Silent cancels and natural ends leave `_opusSyncFadeUntil` untouched — it tracks the last *audible* fade.
- `_syncOpusAudioToVideo()`: drift-corrects each slot. `expectedVideoTime = startVideo + (ctx.currentTime - startCtx) * rate`. Restarts the source if drift > 150 ms OR if `video.playbackRate` changed (the AudioBufferSourceNode's rate can't change mid-stream without an audible glitch).
- J/K speed handlers call `_updateOpusSyncRate(rate)` which re-anchors the timeline (`startVideo` updated to current expected position, `startCtx` to current `ctx.currentTime`) before assigning the new `source.playbackRate.value`.

### Scrub audio preview
- 80 ms snippet via Web Audio at scrub time, throttled at `_SCRUB_THROTTLE` ms.
- `source.playbackRate.value = PLAYBACK_RATES[playbackRateIndex]` so scrub preview matches the user's selected speed (not always 1×).
- Storage: full-quality `AudioBuffer` for Chrome Opus slots (needed for Opus sync replacement). Channel-preserving 22050 Hz downsample via `_downsampleForScrub()` for everything else. The old mono average cancelled anti-phase stereo (`L = −R`) to silence during scrub; every channel must remain independent. The lower sample rate still roughly halves PCM storage versus the source at 48 kHz, but channel count is no longer discarded.
- Grain replacement uses `_phaseAlignScrubOffset()` to correlate the incoming grain against the outgoing one within ±8 ms of the requested position, preventing opposite-phase overlap from producing CENTER-tone/speech dropouts. `_scrubEnvelopeGain()` + `_holdScrubGain()` analytically reconstruct the outgoing grain's instantaneous envelope before replacing its scheduled ramp; do not use `AudioParam.cancelAndHoldAtTime` here—live browser testing produced pronounced clicks despite its intended semantics. Envelope duration is playback-rate-adjusted. The bounded alignment remains well inside one 24 fps frame; never widen it casually because scrub A/V locality matters.
- MP4 edit-list placement is preserved separately in `_audioTimelineStarts`: `bufferTime = videoTime − timelineStart`. Times before the first sample and after the buffer end are silent rather than clamped to an edge sample. This mapping is shared by Chromium and Safari scrub preview; native `<video>` audio remains untouched. Chromium's Opus Web Audio replacement also uses it and schedules a future source start when playback begins inside leading silence. A seek or playback-rate change during that pending interval must cancel and reschedule the source: unlike the ordinary 15 ms fade window, a long timeline-silence wait changes when the video will reach `timelineStart`.

### Audio & video metrics
- EBU R128 / BS.1770-4 in `computeAudioMetrics(audioBuffer)` (`js/audio-viz.js`). K-weighting via two cascaded biquad IIR stages (high-shelf + RLB, coefficients computed analytically per fs via Audio EQ Cookbook). 400 ms gated blocks → integrated LUFS; 3 s short-term blocks → LRA; 4× Catmull-Rom cubic interpolation for true peak per channel.
- Info bar shows `LUFS · LRA · TP`. CSS `:empty { display: none }` auto-hides absent metrics.
- LUFS envelope (E key cycles modes): Waveform / Waveform+LUFS / LUFS only. Short-term LUFS drawn as stepped chart, reference lines at −14 (streaming) / −16 (podcast) / −23 (broadcast).

### Other
- **`endScrubDrag(e)`** (in the scrub closure in `index.html`) is the sole drag finalizer — mouseup routes through it, and so do three **lost-mouseup recovery** paths: mousemove with `e.buttons === 0` (release happened outside the window), `window` blur (Alt-Tab mid-drag), and a mousedown arriving while `isDragging` is still true. A stuck `isDragging` is catastrophic: `playAllMedia` stops suspending scrub decoders (choppy playback) and the drift lock stands down permanently. `e === null` means "no pointer position" (recovery): position-dependent final seeks are skipped and videos settle on `_scrubOverlayLastT`. Guarded by ownership harness (L). **Scrub does not touch `.muted`** (v3.12.2): earlier builds unmuted every `<video>` during a drag as a Chrome decode-warm hack (muted+paused seeks historically skipped frame decode, freezing the scrub preview) and snapshotted/restored the flags — that overloaded `.muted` and collided with the persistent-mute logic (v3.12.1). The quirk was re-verified fixed on modern Chrome (macOS H.264 + Linux VP9, 2026-07), so the unmute/snapshot/restore was removed; the ownership guard (L) now freezes `.muted` out of the scrub path. If a scrub-preview freeze ever resurfaces on some browser, the old approach is in git history.
- Scope rendering uses `Uint16Array` hit counts + `putImageData`; hit buffers cached in `js/scopes.js`.
- Images loaded via `URL.createObjectURL` (not FileReader/base64) — no heap inflation.
- Loading overlay (`#loadingOverlay`) shows status during audio decode; hidden at `startFadeIn()`. `checkAllLoaded()` is called from both the audio `loadedmetadata` path AND the end of `decodeAndComputeAudioSlotViz` (defensive — `loadedmetadata` is sometimes delayed indefinitely on `blob:` URLs).
- Service worker (`sw.js`) early-returns for `blob:` URLs — Chrome cannot fetch blob URLs from within a service worker, and intercepting them blocks `<audio>` element loadedmetadata.
- Pixel magnifier for video uses a **CSS-positioned clone `<video>` element** (not `drawImage(video, canvas)`) because Chrome's macOS video pipeline applies a BT.709-style transfer treatment to `<video>` that canvas content doesn't get — the clone matches by construction. Clipping uses `clip-path: circle(50%)` — `overflow:hidden` + `border-radius:50%` does NOT clip hardware-composited video on macOS. **Fallback if the clone approach ever breaks**: the mismatch was measured empirically for the scrub overlay (2026-07, luma-ramp flicker calibration; residual ≤2/255) and corrected with the `#scrubOverlayColorFix` feComponentTransfer table in `index.html` — a canvas + that filter is a proven drop-in alternative. Caveat: the table captures current Chrome-on-macOS behavior (re-measure after major Chrome color-pipeline changes), whereas the clone is version-proof.

## Naming Conventions

- UI shows two view modes: **Stack** and **Grid** (never "Overlay" or "3-UP").
- Grid sub-layouts (3 files): **Inline** (equal cols/rows) and **Offset** (L-shaped 1+2).
- Internal code still uses `tripartite`, `tripartiteLayout3Col`, etc. — only user-facing text was renamed.
- Slots are named `original`, `editA`, `editB` internally; UI shows "Ref"/"A"/"B" for video/image and "GT"/"A"/"B" for audio (`slotLabel(slot)` returns context-aware labels).

## Coding Conventions

- No build step, no dependencies — vanilla HTML/CSS/JS only.
- CSS is in a single `<style>` block at the top of `index.html`; most JS is in the single `<script>` block at the bottom. Cohesive subsystems are extracted into `js/*.js` classic scripts (see Files) — prefer extending an existing module when the code belongs to its subsystem; otherwise edit `index.html`.
- Use `_prefixed` names for module-level private state (e.g., `_audioSlotVizData`, `_opusSyncSlots`). (Note: `_frameStepping` is referenced in some older comments but does not actually exist — the real suppression flag is `_bulkSyncActive`.)
- Debounced layout functions use the pattern `functionNameDebounced` wrapping `functionName`.
- **Single-owner discipline**: each piece of stateful behavior should have ONE owner (one function that writes it; everyone else routes through it). The ownership harness (`tests/ownership.test.mjs`) enforces this for the audited cases — when adding/refactoring an owner, update the corresponding guard.

### Release checklist (every version bump)

Do **all** of these on every version bump — they are one atomic unit, not optional extras:

1. **Bump `APP_VERSION` in `index.html` and `CACHE_NAME` in `sw.js` together** (guarded by the ownership harness — they must match). The service worker uses `CACHE_NAME` to invalidate the cache for installed PWA users.
2. **Add a "What's New" entry inside `#changelogPopup`** (search for `<h3>v3.x.y</h3>`). The popup auto-shows on version change.
3. **Update the docs for any user-facing change**, and always update `README.md`'s **`**Current version:**`** line to the new number (now guarded by the ownership harness — it must equal `APP_VERSION`). Sweep `README.md` / `FEATURES.md` / `MANUAL.md` for any behavior the release changed (a new feature, a changed default, a new/rebound hotkey) and keep them accurate — stale docs are a release bug.
4. **After pushing to `master`, verify GitHub Pages actually published it.** The Pages *deploy* step (`actions/deploy-pages`) intermittently fails with `Deployment failed, try again later` even when the Jekyll *build* succeeds — a silent failure that leaves the live site on the previous version. Check the latest `pages build and deployment` run for the pushed SHA; if the deploy job failed, **re-run failed jobs** (Actions tab, or `rerun_failed_jobs`) and confirm the live site serves the new `APP_VERSION` before calling the release done.

## Testing

Two layers:
- **Behavioral (Playwright)**: `npm test` / `npx playwright test`. Real headless Chromium; state inspected via `__testAPI`.
- **Structural + pure-logic (`npm run test:ownership`)**: `node tests/ownership.test.mjs`, dependency-free, no browser. Reads concatenated sources (`index.html` + `js/*.js`) and asserts: single-owner guards (RVFC loop chain, video handler binding, decode generations, opus-sync restart, decode pipeline, transport cluster), build/version hygiene (`APP_VERSION` == `CACHE_NAME`; every `<script src=js/*>` is in `sw.js` ASSETS), inline-`<script>` syntax, and pure-function unit tests (incl. the MP4 demuxer against a real fixture). Guards use `countOf`/brace-balancing `extractFn`; each freezes a specific competing-owner bug and is verified to fail when its fix is reverted. Run both before pushing.

- Playwright. `npm test` or `npx playwright test` runs the suite from project root.
- `playwright.config.ts` declares `globalSetup: './tests/global-setup.ts'`, which auto-generates the gitignored MP4 / WebM / WAV / MP3 fixtures via `tests/fixtures/generate.sh` if any sentinel (`tests/fixtures/landscape_a.mp4`, `vorbis_a.webm`, or `vorbis_long.webm`) is missing. Requires `ffmpeg` on PATH; setup errors out with an install hint if it isn't.
- `tests/fixtures/*.{mp4,webm,wav,mp3}` are gitignored (deterministic outputs of the generator script — don't commit them).
- Tests use the `__testAPI` global on `window` to inspect internal state (`zoomLevel`, `fitZoom`, `isGridMode`, `_loopInPoint`, etc.) — add to `__testAPI` when introducing testable state.
- Server: `./start.sh` runs `npx serve -l 8080 .` from project root; Playwright auto-detects and reuses it (`reuseExistingServer: true`).
